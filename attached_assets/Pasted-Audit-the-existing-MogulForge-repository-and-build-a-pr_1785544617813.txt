Audit the existing MogulForge repository and build a production-ready product called:

MogulForge Revenue Rescue™

Revenue Rescue is an AI-powered lead recovery and reactivation platform for home-service contractors.

It imports old leads, missed estimates, website inquiries, CRM contacts, unsold proposals, missed-call records, and dormant opportunities. It cleans and categorizes the data, scores each opportunity, generates personalized reactivation outreach, tracks replies, books appointments, and measures recovered pipeline and revenue.

This must not be built as a standalone page that is copied separately into every client website.

Build Revenue Rescue as a centralized, multi-tenant MogulForge SaaS platform that can power:

1. The main MogulForge Revenue Rescue product.
2. Native Revenue Rescue pages inside websites and CRMs built by MogulForge.
3. Secure embedded Revenue Rescue dashboards inside client websites.
4. Individual embeddable widgets.
5. REST API integrations.
6. Incoming and outgoing webhooks.
7. External CRM integrations.
8. White-labeled client portals.
9. Monthly subscription plans with usage limits.
10. A MogulForge administrator portal for provisioning new clients.

The same hosted application and backend must serve every client organization while maintaining strict tenant isolation.

Do not create separate application copies, databases, or AI logic for each customer.

Reuse the existing MogulForge architecture, authentication, database, routing, design system, components, API conventions, and deployment configuration wherever practical.

Do not break existing MogulForge functionality.

PART 8: SECURE EMBED SYSTEM

  src="https://embed.mogulforge.ai/revenue-rescue.js"
  data-container="mogulforge-revenue-rescue"
  data-module="dashboard">
</script>
<div id="mogulforge-revenue-rescue"></div>

Do not place permanent secret credentials in browser code.

Embed session flow

Implement or prepare this secure flow:

1. A logged-in client user opens their website CRM.
2. The client website backend authenticates that user.
3. The client backend requests a short-lived embed session from MogulForge.
4. MogulForge verifies the client application.
5. MogulForge issues a short-lived signed token.
6. The embed loads using that token.
7. Every API call revalidates the user, tenant, permissions, origin, and expiration.

The token should contain only necessary claims:

* Organization ID
* User ID
* Role
* Permissions
* Enabled modules
* Permitted origin
* Expiration
* Unique token ID

Use short expiration times.

Support token revocation where practical.

Validate:

* Signature
* Expiration
* Approved origin
* Organization
* User status
* Subscription status
* Enabled modules

Protect against:

* Token replay
* Cross-origin abuse
* Unauthorized framing
* Clickjacking
* Cross-tenant access
* Permanent token exposure

Use appropriate Content Security Policy, frame ancestor rules, origin validation, and postMessage validation.
